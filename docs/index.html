Transaction Ledger API

A REST API that keeps a balance for each account and an append-only record of every credit and debit that produced it.

No overdrafts

A debit larger than the balance is rejected and nothing changes.

Safe retries

Each reference_id is unique per account, so a request is never applied twice.

All or nothing

A transaction and its balance update are saved together or not at all.

Immutable history

Transactions can't be edited or deleted, through the API or in the database.

Quickstart

Every endpoint below has a Try it panel that calls this API directly. Follow these steps in order:

  1. Create an account named Alice, then another named Bob. Their IDs are filled into the other panels for you.
  2. Add a credit of 100 to Alice's account.
  3. Transfer 30 from Alice to Bob.
  4. Read Alice's history and check her balance. It should be 70.
  5. Send the credit from step 2 again. You get 409 DUPLICATE_TRANSACTION and the balance stays the same.

Requests & responses

      
    
        
  • Request bodies must be JSON, sent with Content-Type: application/json.
    • 
        
  • Successful responses wrap their payload in data. List responses add a pagination object.
    • 
        
  • Errors always use the same error object. See Errors.
    • 
        
  • IDs are UUIDs generated by the server. Timestamps are UTC, in ISO 8601 format.
    • 
        
  • Amounts are numbers with at most 2 decimal places. They're stored as exact decimals, so 0.1 + 0.2 is exactly 0.3.
    • 
        
  • There is no authentication.
    • 
      

    


    


    

      
Idempotency

      
Every transaction carries a reference_id chosen by the client. Within one account, a reference_id can only be used once. If a request reuses one:

      
    
        
  • No new transaction is created and the balance doesn't change.
    • 
        
  • The API returns 409 DUPLICATE_TRANSACTION, with the original transaction in details.existing_transaction.
    • 
      

      
A client that times out can simply resend the same request. Either the first attempt succeeded and the retry returns 409, or it didn't and the retry applies it once.

      
    
        
  • The same reference_id on different accounts is allowed.
    • 
        
  • The duplicate check runs before the balance check, so retrying a debit that already succeeded returns 409, not 422.
    • 
        
  • A transfer uses its reference_id for both legs. If either account has already used it, the whole transfer is rejected.
    • 
      

    


    

      
Atomicity & consistency

      
Recording a transaction and updating the balance happen inside one PostgreSQL transaction:

      
    
        
  1. Lock the account row (SELECT … FOR UPDATE).
    2. 
        
  2. Reject the request if the reference_id was already used.
    3. 
        
  3. Update the balance, only if it stays at 0 or above.
    4. 
        
  4. Insert the transaction row.
    5. 
        
  5. Commit, or roll back everything if any step failed.
    6. 
      

      
The row lock makes concurrent requests for one account run one after another. Ten parallel debits of 20 against a balance of 100 always give exactly five successes and a final balance of 0.

      
A transfer runs both legs in the same database transaction. If the credit fails, the debit is rolled back too, so a partial transfer can't happen. Both accounts are locked in a fixed order, so opposite-direction transfers can't deadlock.

Pagination

      
The history endpoint returns transactions newest first by created_at, and takes type, page and limit query parameters.

      
    
        
  • total_records counts all matching transactions after the type filter.
    • 
        
  • total_pages is 0 when there are none.
    • 
        
  • A page past the last one returns an empty data array with status 200.
